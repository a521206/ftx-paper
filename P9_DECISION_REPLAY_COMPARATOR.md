# P9 — Decision and Trade Comparator Design

## Two-phase delivery

P9 is intentionally delivered in two phases:

1. **Phase 1 — canonical-run trade comparison.** Run the canonical pipeline
   for the requested date range, use the resulting audit bundle as the
   comparison baseline, and reconcile it with persisted FTX Paper decision
   and fill events. The current `scripts/ftx/compare_pipeline_to_paper.py`
   implementation is the Phase 1 comparator.
2. **Phase 2 — detailed decision replay comparison.** Run both implementations
   against the same deterministic market-input replay and compare the complete
   ordered decision, execution, exit, and ledger streams field by field.

Phase 1 is the practical first-pass diagnostic and does not claim complete
decision parity. Phase 2 is the implementation-cutover gate.

## Simplified objective

### Phase 1 — canonical-run trade comparison

Use the existing outputs instead of building a new shared bundle protocol:

1. Run the canonical pipeline for the requested date range.
2. Capture the canonical run manifest and use its audit bundle as the baseline.
   The report must preserve both the requested date range and the effective
   processed range from the run artifact.
3. Read its generated trade CSV/audit bundle.
4. Read FTX Paper persisted event records, including actual or replayed trades.
5. Normalize both sides into the existing `AuditTrade` shape.
6. Reconcile trades by date, session, vehicle, cell, direction, and entry time.
7. Explain missing, extra, and modified trades in one report.

The comparator must select exactly one Paper event source per run:
--paper-source live or --paper-source replay. The selected source is applied
consistently to decisions, fills, exits, diagnostics, statistics, and the
report manifest; events from the other source must not affect the result.

This is sufficient for the first P9 pass because the practical question is:

> Did FTX Paper produce the same trades, quantities, exits, and P&L as the old
> canonical pipeline over the same date range?

The detailed decision-event comparator is deliberately deferred to Phase 2.
Phase 1 may report exit and P&L fields as `unavailable` when the persisted
Paper events do not provide a reliable linked value. It must not infer those
values from UI projections or timestamps.

Phase 1 answers:

- Did the canonical run and Paper produce the same entry identities?
- Were the same quantities and entry prices used?
- Which canonical trades are missing, extra, duplicated, or modified?
- Which Paper rejection or execution events help explain a difference?

Phase 1 does not answer complete decision parity, ordering parity, stop/score
parity, or economic-outcome parity.

### Phase 2 — detailed decision replay comparison

Phase 2 adds a deterministic replay comparator with a shared input transcript,
without sharing implementation code between `ftx-paper` and the canonical
pipeline. It must:

1. Run both implementations against the same completed market-input fixture or
   holdout replay.
2. Normalize candidate, warmup, rejection, sizing-rejection, acceptance,
   order, fill, exit, and close events into a versioned comparison schema.
3. Compare the complete ordered event stream, including event identity,
   sequence, timestamps, cell, direction, feature values, score factors, stop,
   quantity, outcome, rejection reason, exit mode, and exit result.
4. Compare futures and synthetic vehicles separately, then compare ledgers,
   costs, daily P&L, and drawdown as a downstream economic reconciliation.
5. Classify every difference and record intentional exceptions explicitly.

Phase 2 must not silently downgrade missing fields to `unavailable` when the
field is required by the parity schema. Missing, extra, reordered, or changed
required events are parity failures.

## Run boundary

### Phase 1 run boundary

The canonical side is generated by the existing command:

```powershell
.venv\Scripts\python.exe -m scripts.ftx.runners.run_ftx_pipeline `
  --run --session both --from 2024-01-01 --to 2026-09-30
```

The command already writes:

```text
data/output/ftx_trades_<vehicle>_<session>.csv
data/output/ftx_audit/<date-range>_sessions/
data/output/canonical/<run-id>/manifest.json
```

The comparator must capture the actual effective date range from the canonical
run manifest or its generated artifacts. If the requested end date is beyond
the loaded data, the report must say which final trading date was actually
processed. Paper events must be filtered to that effective range, not merely
to the requested range.

The Paper side is read-only. It reads the configured FTX Paper runtime SQLite
store through its existing `RuntimeStore`/event-reading path, or through the
existing `/api/v1/events` and `/api/v1/trades` projections when the app is
running. It must not mutate or clear event data.

## What counts as a Paper trade (Phase 1)

The primary Paper trade source is persisted `FILL` or `TRADE` events. These
represent completed execution records and are the closest equivalent to a
canonical `RuntimeTrade`.

Decision events are used to enrich and diagnose the trade:

```text
ACCEPTEDDECISION  -> decision_id, date, session, cell, direction, entry context
FILL / TRADE      -> actual fill price and quantity
EXIT / CLOSE      -> exit price, exit time, exit reason, if persisted
ORDER_ACK         -> operational evidence only
REJECTEDDECISION  -> explains canonical-only or Paper-only decisions
SIZING_REJECTED   -> explains no-trade outcomes before execution
```

If Paper currently persists no complete exit event, the comparator should still
produce a decision/fill comparison and mark exit/P&L fields as `unavailable`,
not infer them from UI labels or broker timestamps.

## Proposed implementation (Phase 1)

Create one focused script:

```text
scripts/ftx/compare_pipeline_to_paper.py
```

Use existing code rather than adding a new repository or database query layer:

- load canonical trades with `src.ftx.audit.load_audit_bundle()` when the audit
  bundle exists;
- otherwise load the canonical CSV through the existing audit conversion;
- load Paper events through the existing `RuntimeStore.read_events()` path;
- convert both sides to `src.ftx.audit.AuditTrade`;
- call `src.ftx.audit.reconcile_trades()`;
- write a JSON and CSV report under `data/output/ftx_comparison/`.

The script may have a small Paper-event adapter because Paper events are not
currently shaped as `AuditTrade`. That adapter is a boundary conversion only;
it must not reimplement strategy, sizing, exit, or P&L logic.

## Matching key (Phase 1)

Start with the existing audit identity:

```text
(session, vehicle, date, cell, direction, entry_time)
```

For Paper records, derive:

- `session` from the persisted decision/session field;
- `vehicle` from the order/trade instrument or configured Paper vehicle;
- `date` and `entry_time` from `decision_at`/`minute`, normalized to IST;
- `cell` and `direction` from the linked decision event;
- `quantity` from the fill/trade event.

Do not use `decision_id` as the first matching key because the two pipelines
may intentionally use different ID formulas. Report ID differences separately.

If multiple Paper events map to one identity key, report `duplicate_actual`
and do not silently pick the first row.

## Comparison fields (Phase 1)

For matched trades compare, in this order:

1. entry time and exit time;
2. quantity/lots;
3. entry and exit prices;
4. exit reason/mode;
5. gross P&L;
6. costs;
7. net P&L.

Use exact equality for timestamps, quantities, lots, and reasons. Use the
existing audit numeric tolerance only for persisted floating-point prices and
P&L values, and record the tolerance in the report. Do not compare fields that
are unavailable on one side as zeros.

## Report (Phase 1)

The first version should produce:

```text
data/output/ftx_comparison/
  <run-id>/
    comparison.json
    matched.csv
    missing_from_paper.csv
    paper_only.csv
    modified.csv
    source_manifest.json
```

Top-level summary:

```json
{
  "status": "MATCHED|MISMATCHED|INCOMPLETE",
  "canonical_run_id": "...",
  "paper_store": "...",
  "requested_range": {"from": "2024-01-01", "to": "2026-09-30"},
  "effective_range": {"from": "...", "to": "..."},
  "canonical_trades": 0,
  "paper_trades": 0,
  "matched": 0,
  "missing_from_paper": 0,
  "paper_only": 0,
  "modified": 0,
  "unavailable_fields": [],
  "by_session": {},
  "by_vehicle": {},
  "by_cell": {}

```

For every missing or modified trade, include the linked Paper decision events
and a reason classification:

```text
missing_paper_fill
paper_rejected
paper_sizing_rejected
paper_event_not_linked
extra_paper_trade
quantity_difference
exit_difference
cost_difference
pnl_difference
duplicate_paper_identity
```

## Diagnosis workflow (Phase 1)

The comparator should answer the following in order:

1. Are the date ranges and sessions identical?
2. Are trade counts identical by session and vehicle?
3. Which canonical trades are missing in Paper?
4. For each missing trade, is there a matching Paper rejection or sizing event?
5. Are matched quantities/lots identical?
6. Are exits and exit reasons identical?
7. Is any remaining P&L difference caused by prices, costs, or missing fields?

This prevents mixing three separate questions: decision eligibility, execution
quantity, and economic outcome.

## Test plan (Phase 1)

Add tests to the established audit/comparison test file where possible. Cover:

- canonical audit bundle loading;
- Paper event-to-`AuditTrade` conversion;
- IST timestamp normalization;
- actual versus replayed Paper event selection;
- one-to-one matching by the existing identity key;
- missing, extra, modified, and duplicate trades;
- linked rejection/sizing diagnostics;
- incomplete exit/P&L fields reported as unavailable;
- effective date range and run-manifest capture;
- deterministic JSON/CSV output.

## Scope boundary

Phase 1 owns canonical-run trade eligibility and entry-execution comparison.
It does not rerun Paper strategy logic, compare the complete decision stream, or
claim portfolio-level parity. Phase 2 owns detailed decision replay, exits, and
ledger/economic reconciliation. P10 may consume the Phase 1 matched-trade
report for ledger, cost, daily P&L, drawdown, and cross-vehicle analysis, but
Phase 2 remains the production cutover gate.

## Completion gates

### Phase 1 completion gate

Mark Phase 1 complete when the comparator can run a canonical baseline for the
requested range and produce a reproducible report showing either:

- exact trade parity, or
- every mismatch classified with a linked Paper event or an explicit
  `unavailable` reason.

The Phase 1 report must include the canonical run ID, requested and effective
date ranges, sessions, vehicles, source paths, trade counts, and deterministic
JSON/CSV detail files.

### Phase 2 completion gate

Mark Phase 2 complete only when both implementations have been run against the
same deterministic fixture set and holdout replay, and the report shows zero
unexplained differences in the required decision, exit, and ledger fields.
Every intentional exception must include the exact field, reason, expected
value on each side, and explicit approval before cutover.
