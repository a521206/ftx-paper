# P9 — Decision and Trade Comparator Design

## Simplified objective

Use the existing outputs instead of building a new shared bundle protocol:

1. Run the canonical pipeline for the requested date range.
2. Read its generated trade CSV/audit bundle.
3. Read FTX Paper persisted event records, including actual or replayed trades.
4. Normalize both sides into the existing `AuditTrade` shape.
5. Reconcile trades by date, session, vehicle, cell, direction, and entry time.
6. Explain missing, extra, and modified trades in one report.

This is sufficient for the first P9 pass because the practical question is:

> Did FTX Paper produce the same trades, quantities, exits, and P&L as the old
> canonical pipeline over the same date range?

The detailed decision-event comparator can be added later if trade-level
differences cannot be explained from persisted events.

## Run boundary

The canonical side is generated by the existing command:

```powershell
.venv\Scripts\python.exe -m scripts.ftx.runners.run_ftx_pipeline `
  --run --session both --from 2024-01-01 --to 2026-09-30
```

The command already writes:

```text
data/output/ftx_trades_<vehicle>_<session>.csv
data/output/ftx_audit/<date-range>_sessions/
data/output/canonical/<run-id>/manifest.json
```

The comparator must capture the actual effective date range from the pipeline
run manifest. If `2026-09-30` is beyond the loaded data, the report must say
which final trading date was actually processed.

The Paper side is read-only. It reads the configured FTX Paper runtime SQLite
store through its existing `RuntimeStore`/event-reading path, or through the
existing `/api/v1/events` and `/api/v1/trades` projections when the app is
running. It must not mutate or clear event data.

## What counts as a Paper trade

The primary Paper trade source is persisted `FILL` or `TRADE` events. These
represent completed execution records and are the closest equivalent to a
canonical `RuntimeTrade`.

Decision events are used to enrich and diagnose the trade:

```text
ACCEPTEDDECISION  -> decision_id, date, session, cell, direction, entry context
FILL / TRADE      -> actual fill price and quantity
EXIT / CLOSE      -> exit price, exit time, exit reason, if persisted
ORDER_ACK         -> operational evidence only
REJECTEDDECISION  -> explains canonical-only or Paper-only decisions
SIZING_REJECTED   -> explains no-trade outcomes before execution
```

If Paper currently persists no complete exit event, the comparator should still
produce a decision/fill comparison and mark exit/P&L fields as `unavailable`,
not infer them from UI labels or broker timestamps.

## Proposed implementation

Create one focused script:

```text
scripts/ftx/compare_pipeline_to_paper.py
```

Use existing code rather than adding a new repository or database query layer:

- load canonical trades with `src.ftx.audit.load_audit_bundle()` when the audit
  bundle exists;
- otherwise load the canonical CSV through the existing audit conversion;
- load Paper events through the existing `RuntimeStore.read_events()` path;
- convert both sides to `src.ftx.audit.AuditTrade`;
- call `src.ftx.audit.reconcile_trades()`;
- write a JSON and CSV report under `data/output/ftx_comparison/`.

The script may have a small Paper-event adapter because Paper events are not
currently shaped as `AuditTrade`. That adapter is a boundary conversion only;
it must not reimplement strategy, sizing, exit, or P&L logic.

## Matching key

Start with the existing audit identity:

```text
(session, vehicle, date, cell, direction, entry_time)
```

For Paper records, derive:

- `session` from the persisted decision/session field;
- `vehicle` from the order/trade instrument or configured Paper vehicle;
- `date` and `entry_time` from `decision_at`/`minute`, normalized to IST;
- `cell` and `direction` from the linked decision event;
- `quantity` from the fill/trade event.

Do not use `decision_id` as the first matching key because the two pipelines
may intentionally use different ID formulas. Report ID differences separately.

If multiple Paper events map to one identity key, report `duplicate_actual`
and do not silently pick the first row.

## Comparison fields

For matched trades compare, in this order:

1. entry time and exit time;
2. quantity/lots;
3. entry and exit prices;
4. exit reason/mode;
5. gross P&L;
6. costs;
7. net P&L.

Use exact equality for timestamps, quantities, lots, and reasons. Use the
existing audit numeric tolerance only for persisted floating-point prices and
P&L values, and record the tolerance in the report. Do not compare fields that
are unavailable on one side as zeros.

## Report

The first version should produce:

```text
data/output/ftx_comparison/
  <run-id>/
    comparison.json
    matched.csv
    missing_from_paper.csv
    paper_only.csv
    modified.csv
    source_manifest.json
```

Top-level summary:

```json
{
  "status": "MATCHED|MISMATCHED|INCOMPLETE",
  "canonical_run_id": "...",
  "paper_store": "...",
  "requested_range": {"from": "2024-01-01", "to": "2026-09-30"},
  "effective_range": {"from": "...", "to": "..."},
  "canonical_trades": 0,
  "paper_trades": 0,
  "matched": 0,
  "missing_from_paper": 0,
  "paper_only": 0,
  "modified": 0,
  "unavailable_fields": [],
  "by_session": {},
  "by_vehicle": {},
  "by_cell": {}
}
```

For every missing or modified trade, include the linked Paper decision events
and a reason classification:

```text
missing_paper_fill
paper_rejected
paper_sizing_rejected
paper_event_not_linked
extra_paper_trade
quantity_difference
exit_difference
cost_difference
pnl_difference
duplicate_paper_identity
```

## Diagnosis workflow

The comparator should answer the following in order:

1. Are the date ranges and sessions identical?
2. Are trade counts identical by session and vehicle?
3. Which canonical trades are missing in Paper?
4. For each missing trade, is there a matching Paper rejection or sizing event?
5. Are matched quantities/lots identical?
6. Are exits and exit reasons identical?
7. Is any remaining P&L difference caused by prices, costs, or missing fields?

This prevents mixing three separate questions: decision eligibility, execution
quantity, and economic outcome.

## Test plan

Add tests to the established audit/comparison test file where possible. Cover:

- canonical audit bundle loading;
- Paper event-to-`AuditTrade` conversion;
- IST timestamp normalization;
- actual versus replayed Paper event selection;
- one-to-one matching by the existing identity key;
- missing, extra, modified, and duplicate trades;
- linked rejection/sizing diagnostics;
- incomplete exit/P&L fields reported as unavailable;
- effective date range and run-manifest capture;
- deterministic JSON/CSV output.

## Scope boundary

P9 owns decision/trade eligibility and execution parity. It does not calculate
new P&L, rerun Paper strategy logic, or compare portfolio-level drawdown. P10
will consume the matched trade report for ledger, cost, daily P&L, drawdown,
and cross-vehicle comparison.

## Completion gate

Mark P9 complete when the comparator can run the full requested range and
produce a reproducible report showing either:

- exact trade parity, or
- every mismatch classified with a linked Paper event or an explicit
  `unavailable` reason.
